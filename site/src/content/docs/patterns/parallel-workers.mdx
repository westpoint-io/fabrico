Parallel workers share a job that one [Factory](../../reference/files/glossary/#term-factory) can't keep up with. A [Balancer](../../reference/machines/balancer/) hands [items](../../reference/files/glossary/#term-item) to its outputs in turn, two Factories do the same work side by side, and a [Merge](../../reference/machines/merge/) puts their results back on one line.

The board below has a [Source](../../reference/files/glossary/#term-source), a Balancer, two Factories, a Merge and a Debug [Sink](../../reference/files/glossary/#term-sink), left to right, with [belts](../../reference/files/glossary/#term-belt) between them. Six orders arrive 4 ticks apart. The Balancer hands the odd orders to worker A, the top Factory, and the even orders to worker B, the bottom one, and the Merge brings their results to the Debug Sink.

## How the board works

Press Play and the board stops on these three [ticks](../../reference/files/glossary/#term-tick), the engine's steps:

1. Tick 63: The Balancer hands the first order to worker A, the top Factory. It takes its outputs in turn, so the next order goes to worker B.
2. Tick 105: Worker B, the bottom Factory, runs the same code on order 2. Its belt from the Balancer is one tile longer, so worker A has already done order 3.
3. Tick 165: The Debug Sink logs order 2 after order 5. Each worker did three orders, but worker B's results take longer to reach the Merge.

The Debug Sink logs the orders as 1, 3, 5, 2, 4 and 6. Worker A's results carry `done` 1, 2 and 3, and so do worker B's, because each Factory counts only the orders it took.

## The Factory code

Both Factories run this same code, once for each item that reaches them:

```js title="Factory code"
// pack the order; each worker counts its own
export default function (input, ctx) {
  const done = (ctx.state.done || 0) + 1;
  ctx.state.done = done;
  ctx.emit(0, { order: input.order, done: done });
}
```

`ctx.state` belongs to the Factory that runs the code, so `ctx.state.done = done` keeps a separate count in each worker. Both workers end the run with `done` at 3.

## Trade-offs

- A second worker helps when one Factory falls behind. A Factory whose run emits several items sends them out one a tick and takes no new item until they have gone, so items queue in front of it; [Factory API](../../reference/code-and-http/factory-api/) has the rule. Each run on this board emits one item, so one Factory would have kept up here.
- The Balancer hands items to its outputs in turn, not to whichever worker is free, so a worker that falls behind still gets every other item. [Balancer](../../reference/machines/balancer/) has the rule.
- When the belt to one worker can't take another item, the Balancer holds back, and the other worker gets no new item either: a Balancer sends nothing while either of its outputs is full. [Backpressure](../../concepts/backpressure/) explains how a line packs up from there.
- Each Factory keeps its own <Fact id="factory.ctx.state" />, so the workers share nothing. A count kept there covers only that worker's items, as the two counts of 3 on this board show.
- Results can leave the Merge in another order than the items came in. Here worker B's belts are each one tile longer, so the Debug Sink logs orders 1, 3 and 5 before 2, 4 and 6. Keep a field such as `order` in each item if a later step needs the first order back.
