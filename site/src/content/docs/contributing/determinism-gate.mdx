Fabrico's core has to give the same result from the same starting state and the same events on every run and every computer. No single script guards that. A handful of checks do, and each one fails on a different kind of change. CI runs all of them on every push.

[Determinism and replay](../../concepts/determinism-and-replay/) explains what that promise means on a running board, and where it ends.

## Lints that stop nondeterministic code

[clippy.toml](https://github.com/westpoint-io/fabrico/blob/main/clippy.toml) bans floats, `HashMap` and `HashSet`, the wall clock, ambient random numbers and file, network and process I/O. `fabrico-core`, `fabrico-engine` and `fabrico-player` turn those lints into errors, so a banned type or call in them fails the build under clippy. The CI job named "determinism gate" runs clippy over the workspace with warnings as errors. Run the same line locally:

```bash
cargo clippy --all-targets --all-features -- -D warnings
```

[scripts/check-no-usize-state.sh](https://github.com/westpoint-io/fabrico/blob/main/scripts/check-no-usize-state.sh) fails when a field of a serialized struct is `usize` or `isize`. Those types change size between a desktop build and the wasm player, so the bytes the core writes would change with them. The same CI job runs it.

## Recorded runs that must still replay

[The golden corpus](../golden-corpus/) is a set of recorded runs with the hash of every tick. The certification tests replay each recording and compare every tick with the recorded hash, on Linux, macOS and Windows. The golden corpus job also re-records the corpus from today's generators and fails when the result differs from the committed files, so a change that moves the bytes a generator writes shows up even while the old recordings still replay.

The host parity tests in `crates/fabrico-host/tests/host_parity.rs` run the host's tick loop on the shipped scenes and compare each tick's hash with a committed fixture. A change to the order of work inside a tick fails them. Don't re-record those fixtures to make the test pass; a mismatch is the thing the test exists to report.

## The wasm player against the native build

[scripts/check-wasm-corpus.sh](https://github.com/westpoint-io/fabrico/blob/main/scripts/check-wasm-corpus.sh) replays the corpus in the wasm player under Node and compares each tick with a native run of the same revision. It needs the player built first with `scripts/build-wasm.sh`. CI's wasm player job runs both.

## When one fails

Find out why the output moved before you touch a recording. If the change in behaviour is deliberate, re-record the affected runs as [the golden corpus](../golden-corpus/) page describes, review the diff, and say why in the commit message. If it isn't deliberate, the check has found a bug.
