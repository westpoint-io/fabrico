Fabrico / command-built demo scene

One item in, three fates out

The scene you are looking at is a running pipeline: a timer feeds items into a JavaScript factory, a tee duplicates every result down two branches, and a red fault lane waits underneath for anything that goes wrong. There is no finish line. The simulation reaches a steady state and holds it, deterministically, tick after tick.

The map

Same layout as your screenshot, with each piece numbered. Flow runs left to right; the fault lane runs south.

Amber dots are items (events). Chevrons show belt direction. Green tint means a machine is actively working; the grey fault sink has never received anything. The four bunched dots near 8 are a real queue, not a rendering artifact.

What each piece is

  1. 1
    SOURCE, driven by a timer

    Every 8 ticks (the sim runs 60 ticks per second, so roughly 7.5 times a second) the host timer fires and the source injects one item carrying the payload {}. In a real factory this is where a webhook lands: one POST becomes one logged event. Everything downstream is a pure, replayable consequence of that log.

  2. 2
    Belts: the wires with physics

    A belt is a single-lane queue of slots, 3 per tile, advancing one slot every ticks_per_slot ticks - 2 by default, so a slot every other tick. Length is meaningful twice over: a longer belt adds latency AND buffer capacity. This first belt is 2 tiles, so 6 slots, and an item takes 10 ticks to cross it: traverse-time is (3 × tiles − 1) × ticks_per_slot.

  3. 3
    FACTORY: your code at the boundary

    The 3x3 machine runs user JavaScript in a sandboxed QuickJS context with no clock, no network, and a seeded RNG, so the same input always produces the same output. Items enter the west In port, the script transforms them, and results leave the east Out port. The demo script is a simple pass-through transform.

  4. 4
    The fault lane

    The ringed red nub on the factory's south edge is its Fault port. If the script throws or exceeds its instruction budget, the item is stamped with the error and exits here instead, riding the vertical belt into the rotated dead-letter sink. Faults are ordinary routed items, not a special subsystem: you could just as well wire this belt back around as a retry loop. The demo script never fails, which is why this sink sits idle and grey.

  5. 5
    TEE: the duplicator

    A broadcast splitter. Every item that arrives is deep-copied to BOTH outputs, so from here on each event lives twice: one copy per branch, completely independent.

  6. 6
    Near branch: the fast consumer

    A short 3-tile belt into a sink that keeps up with the arrival rate. Items flow through smoothly and are consumed almost as fast as they appear. A sink is where the factory touches the real world again: send an email, call an API, or (here) simply swallow the item.

  7. 7
    Long branch: backpressure made visible

    An 11-tile belt (33 slots, a minimum of 64 ticks of transit) into a sink that admits items more slowly than they arrive. Items park bumper-to-bumper behind the sink's admission gate: that is the standing queue of four you can see. Nothing is dropped; the belt itself is the buffer, exactly like a backed-up Factorio belt.

  8. 8
    Far sink: the slow consumer

    It drains at the same average rate items arrive, just with a delay, so the queue holds steady at about four instead of growing forever. If it were slower still, the queue would creep backward up the belt until the belt filled and the tee could no longer deliver.

One item's journey

Follow a single injection from birth to consumption. Ticks are approximate; the sim advances 60 per second, so this whole story takes under a second and a half.

  1. TICK 0

    Timer fires. The source logs one event and places an item on the first belt. This log entry is the only input; everything after is derived.

  2. TICK ~6

    Item crosses the 2-tile belt and enters the factory's In port.

  3. SAME TICK

    The sandboxed JS runs inside its gas budget and emits the transformed item on Out. Had it thrown, the item would exit the red fault port south instead.

  4. TICK ~12

    Item reaches the tee and is duplicated: copy A north-east, copy B east.

  5. TICK ~21

    Copy A crosses the short belt and is consumed by the fast sink. Half the story is already over.

  6. TICK ~45+

    Copy B finishes the 11-tile crossing, then waits its turn in the queue of four before the slow sink admits it. Consumed a few ticks later.

  7. NEVER (SO FAR)

    No item has taken the fault lane. The grey sink at the bottom is the proof.

So what happens "by the end"?

There is no end, only equilibrium The simulation never terminates; it settles. After the first second or so the scene reaches a steady state and holds it forever: one item born every 8 ticks, two copies made at the tee, the fast sink consuming instantly, the slow sink consuming behind a constant four-item queue, and the fault lane empty. Every item ever created is accounted for: consumed by a sink or visibly in flight on a belt. Nothing is lost.

And it is exactly reproducible Because every input enters as a logged event and every machine is deterministic, replaying the log reproduces this scene byte for byte: the same queue of four, in the same slots, at the same tick. Pause it, save it, reload it, replay it from genesis; you always arrive at this same picture. That property is the point of the whole engine: the demo is a factory game to watch, but it is also an auditable automation pipeline you could rewind.
